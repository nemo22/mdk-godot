## Validation

`p2work/combined.py` disassembles every script of LEVEL3..8.CMI with part 1 (`p1/dis.py`), part 2
(`opcodes_part2.json`) and part 3 (`opcodes_part3.json`), starting at the directory 0 and 2 entries and at the
arena scripts of directory 3 (record = pstr, pstr, u32 offset), and following every off32 code target.

- The off32 operands of part 3's 150 and 206 are treated as data pointers.
- 66,649 instructions are decoded, and no instruction overlaps another one's start (0 conflicts).
- The only unknown opcode is 0x8D at the start of the arena script `HMO_9` of level 3 (file 0x1c99a). That script
  is probably never used.
- Of the unreached byte ranges between the directories and the first model, 820 decode linearly with no errors
  and end exactly where the next reached code starts (dead code after gotos). The other 97 are data, such as paths
  and arena records, and none of them fails on a part 2 opcode.
- Every part 2 action byte is 0xFC, 0xFD, 0xFE or 0x0C, and every condition op is 1..8.
- Opcodes that never occur: **70, 182, 225**. Opcodes that occur only once: 126, 157, 197.

## Shared operand encodings

**value** (kind `value`) = `u8 src; src==3 ? f32 immediate : u8 index`. It is read through
`0x440944 var_ptr(obj, src, index)`:

| src | variable |
|---|---|
| 0 | global var `0x573b4c[i]` (4 floats) |
| 1 | arena var `(obj+0x60)+0x48[i]` |
| 2 | own var `obj+0x234[i]` |
| other | linked object's var `(obj+0x2b8)+0x234[i]`, or a dummy (0x491eac) without a link |

An index outside 0..3 becomes 0. Opcodes 65/66/216/67/182/183 use the plain pair `u8 src, u8 index` with the same
table, so src 3 is a linked-object variable there, not an immediate.

**flag word** (`0x440a34 flags_ptr(obj, src)`, opcodes 68-72):

| src | flag word |
|---|---|
| 0 | `0x573b5c` |
| 1 | arena+0x58 |
| 2 | obj+0x244 |
| 5 | obj+0x312 when obj+0x14a bit 4 is set, else a dummy (0x491eb0) |
| other | (obj+0x2b8)+0x244, or the dummy |

The bit number is `u8 & 31`.

**cond** (kind `cond`) = `u8 op; f32 a; [f32 b if op is 7 or 8]`, tested by `0x45da90(op, x, a, b)`:

| op | condition |
|---|---|
| 1 | x < a |
| 2 | x > a |
| 3 | x < a+0.05 |
| 4 | x > a-0.05 |
| 5 | abs(x-a) < 0.05 |
| 6 | abs(x-a) >= 0.05 |
| 7 | a <= x <= b |
| 8 | x <= a or x >= b |
| else | false |

**action** (kind `action`, the last operand of every "if" opcode) = `u8 kind`, then:

| kind | operands | condition true | condition false |
|---|---|---|---|
| 0xFE | off32 then, off32 else | gosub then | gosub else |
| 0xFC | off32 target | gosub | nothing |
| 0x0C | off32 target | goto | nothing |
| 0xFD | none | return | nothing |

- 0xFC and 0x0C convert offset 0 to NULL.
- Any other kind has no operand bytes and takes the goto path with a stale `[ebp-0xb8]` (never seen in the data).
- It is executed after all operands are read, so the return address is the next instruction.
- **goto**: `obj+0x108 = pc = target` and `obj+0x26c[depth] = 0` (u16).
- **gosub**:
  - If depth `obj+0x248 >= 4`, it calls `0x440300` (a log only), sets `obj+0x108 = 0` and returns from script_run.
  - Otherwise it pushes `obj+0x24c[depth] = return pc` and `obj+0x25c[depth] = obj+0x108`, does `depth++`, sets
    `obj+0x108 = pc = target` and `obj+0x26c[depth] = 0`.
- **return**: at depth 0 it logs, clears obj+0x108 and returns from script_run. Otherwise `depth--`,
  `pc = obj+0x24c[depth]` and `obj+0x108 = obj+0x25c[depth]`.

So obj+0x108 is the restart point of the current routine: the next frame resumes there.

Other complex operands (all described exactly in the JSON `layout` fields):

| op | layout |
|---|---|
| 61 | `u8 mode; mode==0 ? u8 point : pstr part` |
| 83 | `0xFF, f32 target, f32 rate` if the next byte is 0xFF, else a value |
| 159 | `u8 mode; [3 x f32 if mode is 1 or 2]` |
| 189 | `u8 mode; mode 0: 2 x f32, mode 1: f32, else nothing` |
| 193 | `u8 mode; [pstr if mode==3]` |
| 245 | `0x00, u8 mode, pstr` if the next byte is 0, else `pstr` |
| 248 | `u8 mode; f32; mode==0 ? 2 x f32 : f32` |

**Target point.** At entry, script_run copies Kurt's position `0x5739c0` into `0x57fc34` (x, y, z) and his yaw
`0x5739f0` into `0x57fc30`. When `obj+7 != 2`, it uses the active decoy `0x573c20` instead (its +0x10 and +0x4c), or
the object in `0x491e48`. "Target" in the summaries means this point. "Kurt's real position" means `0x5739c0`.

## Bugs and quirks (keep them in mind when emulating)

- **182 switch_goto** reads `u8 src, u8 idx, u8 n, n x off32`, but its skip loop never advances pc:
  - When `0 <= v < n`, it always goes to entry [1].
  - When v is out of range, execution continues at table+4 (inside the table).
  - It never occurs in the game data. The intended behaviour is surely "goto entry[v]".
- **183 switch_gosub** is correct in range (gosub entry[v], return after the table). Out of range it has the same
  bug: it continues at table+4. It is used 26 times, probably always in range.
- **49 release_children** executes the action inside its loop, once per missing child. It has no else branch.
- **193** needs both velocity components to be non-zero before it changes yaw (the test is `vx != 0 && vy != 0`).
  Mode 2's pitch has the same test.
- **184** calls the radius-damage and kill helpers with stale EBX/ECX/EDX register arguments.
- `0x40a2d0` is named `fatal_error` in names.txt, but it only appends to `debug.err` when debugging (`0x5742f8`) is
  on. It does not quit. The same applies to "Bullet %s not found" (61) and to 77's message.
- The angle helpers use degrees.
  - `0x440220(y, x)` = atan2 in [0,360), with 0 when both are 0.
  - `0x440288(a, &sin, &cos)`.
  - Forward is (cos yaw, sin yaw).
- Several opcodes (80, 235, 105, 248 mode 0, and `0x45d770` used by 159) use the engine's "local offset" formula
  `(-a*cos - b*sin, -b*cos - a*sin)`. It is not a plain rotation, so it must be reproduced literally.

## Uncertain / open

- Motion codes 43/197/221/229/78/74/61/30 are handled by per-frame movement code outside the interpreter (for
  example 0x45a7d4). A port needs those updaters too.
- The meaning of obj+0x2c4 (177), obj+0x276/0x277 (74), the +0x302 union and obj+0xec is not fully known.
- The 0x491e48 "kind 1" object is probably a player-side object such as a helper. Not checked.
